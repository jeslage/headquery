# Typed schema

The Statamic addon exports your content model (collections, taxonomies, globals, their
blueprints and `allowed_filters`) as a CMS-neutral JSON schema. `@headquery/codegen` turns
it into a TypeScript module.

The CLI is the `headquery` bin of `@headquery/codegen` and has two commands:

| Command | Description |
| --- | --- |
| `headquery init` | Run once: asks for the CMS base URL (or a schema file; suggests `HEADQUERY_BASE_URL` from the environment, `.env.local` or `.env`) and the output path, and writes `headquery.config.ts` (`.mts`/`.mjs` where needed). Then it offers to write a typed client file, add `cms:types` scripts to `package.json` and add `HEADQUERY_*` lines to the env file. See below. |
| `headquery generate` | Fetches the schema and writes the types. Reads the config file; flags below override it. |

What `init` writes, besides the config:

| Step | Details |
| --- | --- |
| Client file | Only when an adapter (`@headquery/statamic`) is installed. Written next to the generated types (`src/cms.ts`), passes `Schema` explicitly and reads the base URL from env depending on the framework: `NEXT_PUBLIC_HEADQUERY_BASE_URL` (Next.js), `VITE_HEADQUERY_BASE_URL` (Vite), `HEADQUERY_BASE_URL` (Node), a literal URL for Nuxt (use `runtimeConfig`). The framework is detected from `package.json` and can be changed in the prompt. An existing file is only overwritten after confirmation or with `--force`. |
| `package.json` scripts | `cms:types` (`headquery generate`) and `cms:types:check` (`headquery generate --check`). Existing scripts are never changed. |
| Env lines | `HEADQUERY_BASE_URL`, `HEADQUERY_SCHEMA_TOKEN` (empty) and the client's variable, appended to `.env.local` or `.env` (if neither exists, `init` asks for a name). Keys that are already set stay unchanged. The config then loads that file with `process.loadEnvFile`. `init` warns if the file isn't in `.gitignore`. |

Flags of `headquery init`:

| Flag | Description |
| --- | --- |
| `--base-url` / `--from` | Schema source (CMS origin, or a schema URL/file) |
| `--out` | Output `.ts` file for the types |
| `--framework` | `next`, `nuxt`, `vite` or `node` (default: detected) |
| `--no-client`, `--no-scripts`, `--no-env` | Skip a step |
| `--env-file` | Env file to add the lines to |
| `--yes` | No prompts: use flags and defaults, all steps on |
| `--force` | Overwrite an existing config and client file |

Before `@headquery/codegen` is installed, run `npx @headquery/codegen init`: `npx headquery`
would look for an npm package called `headquery`.

```bash
npx headquery generate --from schema.json --out src/cms.generated.ts
```

Options of `headquery generate`:

| Flag | Description |
| --- | --- |
| `--from` | Schema source: full http(s) URL of the schema endpoint, or a local JSON file |
| `--base-url` | CMS origin instead of `--from`; fetches `<base-url><api-prefix><schema-path>` |
| `--api-prefix` | API prefix of the CMS (default: `/api`) |
| `--schema-path` | Schema route below the API prefix (default: `/headquery/schema`) |
| `--out` | Output `.ts` file |
| `--token` | Bearer token for the schema endpoint (default: `$HEADQUERY_SCHEMA_TOKEN`) |
| `--target` | Adapter target (default: taken from the schema, e.g. `statamic`) |
| `--module` | Module to augment (default: `@headquery/<target>`) |
| `--check` | Don't write; exit 1 if the output file is out of date (for CI) |
| `--config` | Config file (default: `headquery.config.{ts,mts,mjs,js}` in the current directory) |

## Config file

Instead of passing flags every time, add a `headquery.config.ts` next to your
`package.json` (`headquery init` writes one for you). The CLI finds it automatically, so the
command becomes just `npx headquery generate` (or `npx headquery generate --check` in CI).

```ts twoslash
import { defineConfig } from "@headquery/codegen";

export default defineConfig({
  from: { baseUrl: "https://cms.example.com" }, // → https://cms.example.com/api/headquery/schema
  out: "src/cms.generated.ts",
  token: process.env.HEADQUERY_SCHEMA_TOKEN,
});
```

`from` is one of:

- `{ baseUrl, apiPrefix?, schemaPath? }`: the CMS origin, like the client's `baseUrl`. `apiPrefix`
  defaults to `/api` (as in the client) and `schemaPath` to `/headquery/schema`. Change them if
  you changed `statamic.api.route` or `headquery.schema.path` on the CMS.
- a full http(s) URL of the schema endpoint.
- a local JSON file, e.g. `"./schema.json"` from `php please headquery:schema`.

How the config file is found and applied:

- Supported names, in order: `headquery.config.ts`, `.mts`, `.mjs`, `.js`. Use `--config` for any other path.
- Relative `from` and `out` paths resolve against the config file's directory, so it doesn't matter where you run the CLI from.
- Flags override the config (e.g. `--out` for a one-off run; `--from` or `--base-url` replace `from`). The token falls back to `$HEADQUERY_SCHEMA_TOKEN`.
- The config is a regular module, so you can compute values in it. `.env` files aren't loaded automatically; call `process.loadEnvFile(".env.local")` in the config if you need them.
- `.ts` configs are loaded by Node's built-in type stripping (Node ≥ 22.18). On older Node, name the file `headquery.config.mjs` instead.

## How registration works

The generated file declares one interface per resource (`BlogEntry`, `TagsTerm`,
`SettingsGlobal`, …) and registers a `Schema` through module augmentation:

```ts
declare module "@headquery/statamic" {
  interface Register {
    schema: Schema;
  }
}
```

Pass the generated `Schema` to the client, as the client file from `headquery init` does:

```ts
import { createStatamicClient } from "@headquery/statamic";
import type { Schema } from "./cms.generated";

export const cms = createStatamicClient<Schema>({ baseUrl: "https://cms.example.com" });
```

Collection handles autocomplete, `.where()` only accepts filterable fields, and `.fields()`
narrows results.

Importing the file once (`import "./cms.generated"`) also registers the schema globally, so
`createStatamicClient()` is typed without the generic. That relies on TypeScript seeing the
generated file and resolving the same `@headquery/statamic` copy, so the explicit generic is the
more robust default.

Without a registered schema, the client falls back to loose types: any handle, any field,
items typed as `{ id: string } & Record<string, unknown>`.

The explicit generic also lets you talk to two CMS instances: generate one file per instance and
pass each `Schema` to its own client.

## Field mapping

| Statamic | TypeScript |
| --- | --- |
| `text`, `textarea`, `markdown`, `slug` | `string` (`\| null` unless required) |
| `integer`, `float`, `range` | `number` |
| `toggle` | `boolean` (never null) |
| `date` | ISO `string` |
| `select`, `button_group`, `radio`, `checkboxes` | `HqOption<"a" \| "b">` (`{ key, value, label }`; all `null` when empty) |
| `assets` | `HqAsset` or `HqAsset[]` (`max_files`) |
| `entries`, `terms`, `users` | `HqRelatedEntry`, `HqRelatedTerm`, `HqUser` |
| `grid`, `replicator` | arrays of typed rows/sets (`[]` when empty) |
| `bard` | `HqRichText` (HTML string without sets, blocks with sets) |
| unknown fieldtypes | `unknown` — see [custom fieldtypes](/cms/statamic/custom-fieldtypes) |

System fields Statamic adds to every entry, term and global set (`id`, `url`, `status`,
`permalink`, …) come from `HqEntryBase`, `HqTermBase` and `HqGlobalBase`. Blueprint
fields with the same handle take precedence.
