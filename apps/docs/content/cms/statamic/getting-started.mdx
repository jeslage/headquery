# Getting started with Statamic

This guide takes you from a Statamic site to a typed query in your frontend. It needs
Statamic 5 or 6 with a [Pro license](https://statamic.com/pricing) (the REST API is a Pro
feature) and PHP ≥ 8.2.

<Steps>

### Turn on Statamic's REST API [#rest-api]

headquery wraps Statamic's [REST Content API](https://statamic.dev/rest-api). It is off by
default. In the CMS's `.env`:

```dotenv
STATAMIC_PRO_ENABLED=true
STATAMIC_API_ENABLED=true
```

Then enable the resources you want to query in `config/statamic/api.php`:

```php
'resources' => [
    'collections' => [
        'blog' => [
            'allowed_filters' => ['title', 'slug', 'featured'],
        ],
    ],
    'taxonomies' => true,
    'globals' => true,
    'navs' => true,
],
```

- Only enabled resources end up in the generated types, and only they can be queried.
- Only `allowed_filters` fields can be used in `.where()`. Statamic answers other filters
  with `422`, and the generated types reject them at compile time.

The API route defaults to `/api` (`statamic.api.route`). If you change it, set `apiPrefix` in
the client and `from.apiPrefix` in the [codegen config](/codegen/config).

### Install the addon [#addon]

```bash
composer require headquery/statamic
php artisan vendor:publish --tag=headquery-config   # optional: config/headquery.php
```

The addon only exports your content model; it doesn't change how the REST API answers.
`config/headquery.php` holds the schema endpoint settings and mappings for
[custom fieldtypes](/cms/statamic/custom-fieldtypes).

### Make the schema available [#schema]

<Tabs items={["Same repo (file)", "Separate frontend (endpoint)"]} storageKey="schema-source">
  <Tabs.Tab>
    The frontend lives next to the CMS, so it can read an exported file. Export the schema
    from the CMS project:

    ```bash
    php please headquery:schema --out=schema.json
    ```

    Run it again whenever you change a blueprint or `config/statamic/api.php`.
  </Tabs.Tab>
  <Tabs.Tab>
    The frontend fetches the schema from the CMS. Turn on the schema endpoint in the CMS's `.env`:

    ```dotenv
    HEADQUERY_SCHEMA_ROUTE=true
    HEADQUERY_SCHEMA_TOKEN=a-long-random-token
    ```

    The endpoint stays off (404) until both are set. See [Schema endpoint](#schema-endpoint)
    for the route and its security.
  </Tabs.Tab>
</Tabs>

Not sure which one? See [schema sources](/codegen#schema-sources). If the CMS caches its
config, clear it after changing `.env`: `php artisan config:clear`.

### Run `init`

<Tabs items={["Same repo (file)", "Separate frontend (endpoint)"]} storageKey="schema-source">
  <Tabs.Tab>
    ```bash
    npx headquery init --from ../cms/schema.json
    ```
  </Tabs.Tab>
  <Tabs.Tab>
    ```bash
    npx headquery init --base-url https://cms.example.com
    ```
  </Tabs.Tab>
</Tabs>

`init` asks a few yes/no questions and then writes:

| File | What |
| --- | --- |
| `headquery.config.ts` | Where the schema comes from and where the types go |
| `src/cms.ts` | A typed client that reads the CMS URL from env, the way your framework expects |
| `package.json` | `cms:types` and `cms:types:check` scripts |
| `.env.local` / `.env` | `HEADQUERY_BASE_URL`, `HEADQUERY_SCHEMA_TOKEN` and the client's URL variable (endpoint only) |

Existing files and keys are never overwritten without asking. All options:
[`headquery init`](/codegen/init).

<Callout type="info">
  Haven't installed `@headquery/codegen` yet? Run `npx @headquery/codegen init` instead.
  `npx headquery` looks for an npm package called `headquery`.
</Callout>

### Generate the types

With the endpoint, first set `HEADQUERY_SCHEMA_TOKEN` in the env file to the token from the
CMS. Then:

```bash
npm run cms:types
```

This writes `src/cms.generated.ts`. Run it again whenever the content model changes, and run
`npm run cms:types:check` in CI to catch outdated types. If it fails, the CLI prints the
likely cause; all errors are listed under [Troubleshooting](/cms/statamic/troubleshooting).

### Query

Import the client from `src/cms.ts`. Collection handles, filterable fields and result types
now come from your content model:

```ts twoslash
import "./generated/cms.generated";
import { createStatamicClient } from "@headquery/statamic";
const cms = createStatamicClient({ baseUrl: "https://cms.example.com" });
// ---cut---
// import { cms } from "./cms";

const { data: posts } = await cms
  .collections("blog")
  .where("featured", true)
  .sort("-date")
  .fields(["title", "slug", "date"])
  .get();

posts[0]?.title;
//        ^?
```

</Steps>

## Schema endpoint [#schema-endpoint]

With `HEADQUERY_SCHEMA_ROUTE` and `HEADQUERY_SCHEMA_TOKEN` set, the addon answers at
`GET /api/headquery/schema` (below `statamic.api.route`; the path is `headquery.schema.path`).
In the frontend, `from: { baseUrl }` in the [codegen config](/codegen/config) points there,
and `HEADQUERY_SCHEMA_TOKEN` must hold the same token.

<Callout type="info">
  The endpoint is **off by default**. It only answers when both variables are set.
</Callout>

- `404` unless `HEADQUERY_SCHEMA_ROUTE=true` **and** `HEADQUERY_SCHEMA_TOKEN` is set.
- `401` without the correct `Authorization: Bearer <token>`. The token is compared in
  constant time.
- Responses carry an `ETag`. Unchanged schemas answer `304 Not Modified`.

The schema describes your content model (handles, field names and types), not your content.
Treat the token like any other deploy secret anyway.
